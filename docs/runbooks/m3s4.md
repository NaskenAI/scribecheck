# Runbook: M3 session 4, first real measurement

The first real runs of scribecheck's full mode, on the Gate 1(b) development subset
(`runs/gate1b/subset_spec.json`: 51 notes over 10 consultations; 23 omission notes, 10
clean notes, 8 additions and 10 changes). Development data only. Every run here is made
by a person in a normal terminal, with their own keys; Claude Code makes none of them.

Every run uses **Pass A only** (`passes = ["a"]`), **live calls** (`batch --live`), the
**strict standard** and the **scribecheck pipeline**, as set in the configs in
`docs/runbooks/m3s4/`. Outputs go under `runs/m3s4/` (gitignored).

These numbers are indicative. With 23 omission notes and 10 clean notes, one note moves
detection by about 4 points and false alarms by 10, so treat differences of a few notes as
noise.

## 1. Claude Sonnet 5.5 at effort medium, then high

Check the prices in the two configs against Anthropic's pricing page first. Each run has a
$15 cap; when it is reached the remaining items are reported as unchecked
(`cost_cap_reached`) and the scorer counts them.

```bash
export ANTHROPIC_API_KEY=...   # in your shell only

scribecheck batch runs/m3s4/cases --live --config docs/runbooks/m3s4/claude-medium.toml \
    --format json --output runs/m3s4/claude-medium/batch.json
python scripts/score_run.py score --run runs/m3s4/claude-medium \
    --pairs data/omissionbench/pairs/dataset_v2.json --spec runs/gate1b/subset_spec.json \
    --manifest runs/m3s4/cases/manifest.json \
    --released data/omissionbench/judge_scores --gate1b runs/gate1b/harness-results

scribecheck batch runs/m3s4/cases --live --config docs/runbooks/m3s4/claude-high.toml \
    --format json --output runs/m3s4/claude-high/batch.json
python scripts/score_run.py score --run runs/m3s4/claude-high \
    --pairs data/omissionbench/pairs/dataset_v2.json --spec runs/gate1b/subset_spec.json \
    --manifest runs/m3s4/cases/manifest.json \
    --released data/omissionbench/judge_scores --gate1b runs/gate1b/harness-results
```

`batch` creates the output folder and checks it can write there before making any call, so
a run's reports are never lost at the end. It prints the endpoint warning
(api.anthropic.com is not local) and, at the end, the calls, estimated cost and wall-clock
time. Add `--show-facts` to a `score` command to see
the removed fact next to each matched flag's fact when spot-checking the correct-fact
lines; the output then contains benchmark fact text, so keep it with the run.

Detection and false alarms count Pass A omission flags only. A note whose Pass A could not
finish (for example when the cap was reached) is listed and left out of the rates, not
counted as clean. The correct-fact rate is provisional: matching needs a shared
distinctive word, the same numbers and the same negation, but treat it as an upper bound
until you have spot-checked the matched lines with `--show-facts`.

Partial verdicts (the note carries part of a fact) are information, not flags: the scorer
leaves them out of detection and false alarms, for runs made before and after that change;
add `--partial-as-flags` to count them as flags. The run configs set
`[report] pass_a_trace = true`, so each report also records every extracted fact's path
through Pass A. To see where each omission note's removed fact went (not extracted,
contextual, judged present or partial, rescued by the second look), run:

```bash
python scripts/score_run.py misses --run runs/m3s4/claude-high \
    --pairs data/omissionbench/pairs/dataset_v2.json --spec runs/gate1b/subset_spec.json \
    --manifest runs/m3s4/cases/manifest.json
```

The claude-medium run predates the trace, so for it `misses` can only tell detected and
judged partial from no matching flag.

`docs/runbooks/m3s4/run_effort.sh` runs medium again on the current code (into
`runs/m3s4/claude-medium-v2/`) and high, then scores both and traces their misses into
`runs/m3s4/compare_effort.txt`. `docs/runbooks/m3s4/run_v3.sh` runs medium with the
`scribecheck_v3` prompts (atomic facts) into `runs/m3s4/claude-medium-v3/` and writes its
score and misses beside claude-medium-v2's into `runs/m3s4/compare_v3.txt`.
`docs/runbooks/m3s4/run_v4.sh` does the same for `scribecheck_v4` beside v3
(`runs/m3s4/compare_v4.txt`). `docs/runbooks/m3s4/run_v4_full.sh` runs v4 on all 65
development consultations (265 errored and 65 clean notes; `claude-medium-full.toml`, $25 cap)
and scores it against the released B3 r1 and power-gepa-high records
(`runs/m3s4/score_v4_full.txt`). `docs/runbooks/m3s4/run_judge.sh` then judges each omission
note's correct-fact match with Claude Sonnet 5.5 at effort low (`judge.toml`, $3 cap; fact
texts only), caches the judgements in the run folder, and writes the score and misses with
the judge's matches (`runs/m3s4/score_v4_full_judged.txt`), the severity agreement
(`docs/evidence/severity_agreement_v4.md`) and a 30-pair spot-check sample
(`docs/review/correct_fact_sample.csv`); see `docs/evidence/fact_matching_v4.md`.
`docs/runbooks/m3s4/run_v5_full.sh` ran `scribecheck_v5` the same way into
`runs/m3s4/claude-medium-v5-full/` and scored it beside v4-full (`runs/m3s4/score_v5_full.txt`).
v5 was worse than v4 at every matched false-alarm rate
(`docs/evidence/v5_negative_result.md`). The default prompt set is now the frozen
`scribecheck_v4` (tag `m4-candidate-v4`), under which the v5 code does not run, so
`run_v5_full.sh` refuses to run (check out d55c5ac to reproduce it).
Route one's correct detection needs its flagged-fact text. The split keeps it for development
rows only, as `baseline_facts` in judge_scores, from the commit that added it (23676c9). The
development split must be re-run since then: by a person, with its original arguments and
both previous outputs moved aside. `run_judge.sh` then judges route one's facts with
`--released`, and `judge` stops before any call while no development row carries them.
Route two (power-gepa-high) gives a score and no named omissions, so its correct detection is
not applicable: score-only method.

What to compare between medium and high: detection and false alarms (decision rule and
the k-and-c sweep), the correct-fact rate, cost and calls per note, wall clock, and the
unchecked counts (`quote_unverified`, `model_parse_failure`, `cost_cap_reached`). They
feed the choice of one effort level before Gate 2.

Result: medium and high gave the same detection, correct detection and false alarms, and
high cost about 9% more, so the run effort is fixed at medium (`docs/spec.md`, "Models").

## 2. One open-weight model through OpenRouter

Find today's candidates (reads OpenRouter's public listings only: no key, no model calls):

```bash
python scripts/openrouter_candidates.py
```

It lists open-weight models of at most 40B parameters (total, never active) with at least
32k context and a provider that supports every parameter the config sends with
`require_parameters` (structured output, seed, temperature and max tokens), newest first,
with each provider's quantization and prices, and marks the cheapest provider at FP8 or
better to pin (none is marked if no provider runs at FP8 or better). Models whose size it
cannot read are listed at the end for a check by hand. **Prefer the newest
family among the candidates it lists that meet the criteria**, and check its licence on the
Hugging Face page it names (commercial use must be allowed; Gemma and Llama licences need
review). Families to expect, from before this runbook was written and to be confirmed by
the script: Qwen3 32B (Apache-2.0, dense), Mistral Small 3.2 24B (Apache-2.0), gpt-oss-20b
(Apache-2.0, MoE).

Then fill in the three marked lines of `docs/runbooks/m3s4/openrouter.toml` (model id,
provider to pin, prices), record the quantization the script showed, and run:

```bash
export OPENROUTER_API_KEY=...   # in your shell only

scribecheck batch runs/m3s4/cases --live --config docs/runbooks/m3s4/openrouter.toml \
    --format json --output runs/m3s4/openrouter-<model>/batch.json
python scripts/score_run.py score --run runs/m3s4/openrouter-<model> \
    --pairs data/omissionbench/pairs/dataset_v2.json --spec runs/gate1b/subset_spec.json \
    --manifest runs/m3s4/cases/manifest.json \
    --released data/omissionbench/judge_scores --gate1b runs/gate1b/harness-results
```

The cap is $3. The run refuses to start without `[model.prices]`, because a cap cannot be
enforced without prices. These results are indicative only: a hosted provider's serving
stack is not the one the local headline will use.

## 3. The local path on a laptop (8 GB Apple M3)

For trying the tool, not for accuracy.

```bash
brew install ollama
OLLAMA_CONTEXT_LENGTH=16384 ollama serve     # in its own terminal; see the note below
ollama pull qwen3:4b                         # or phi4-mini (3.8B), or gemma3:4b
python scripts/smoke_model.py --base-url http://localhost:11434/v1 --model qwen3:4b
```

The smoke test prints the model id, token usage and whether the JSON parsed, plus no
endpoint warning (localhost is local).

Ollama's default context window is too small for full-mode prompts, hence
`OLLAMA_CONTEXT_LENGTH=16384`. **If Ollama is too slow or fails to load the model at
16384, restart it with `OLLAMA_CONTEXT_LENGTH=8192`.** (A Modelfile with
`PARAMETER num_ctx 16384` does the same per model.) Ollama trims a prompt longer than its
context window without an error, and the context also has to hold the reply
(`max_tokens = 4096` in `ollama.toml`), so at 8192 a long transcript can be cut short:
fine for trying the tool on demo-001, not for judging the model.

Then a full-mode check of demo-001:

```bash
DEMO=$(python -c "import scribecheck, os; print(os.path.join(os.path.dirname(scribecheck.__file__), 'demo'))")
scribecheck check -t "$DEMO/demo-001.transcript.json" -n "$DEMO/demo-001.note.md" \
    --config docs/runbooks/m3s4/ollama.toml
```

`check` always calls the model live. If you pulled a different model, change `name` in
`ollama.toml` to match.
